复现探针（源码见 `evidence-2026-10-05/probe_test.go.txt`，输出见 `evidence-2026-10-05/probe-run.txt`）：

- FIFO 与 Unix socket 都会让整次扫描返回 `unsupported filesystem entry`，不产生清单（审核时行为；第六轮按 F08 改为跳过并告警，见 1.5 节）。
- 仅执行 `chmod` 的 8 MiB 文件在增量扫描中出现 `reused_files=0 chunked_files=1 content_bytes_chunked=8388608`，而前后 chunk 边界与哈希完全一致。
- 原地改写并恢复 `mtime`、保留 `size` 时，ctime 变化使复用条件不成立，哈希由 `991204fb…` 变为 `900dfeb7…`——普通改写不会静默复用旧哈希。
- 流式分块与单缓冲参考实现在 10 组输入（空文件、1 字节、跨 4 MiB 随机、全零、零前缀、中间零段等）上边界、偏移、大小、哈希与 Zero 标记全部一致。
- `fullZeroChunkBoundary() == chunkMaxSize == 4194304`，4 MiB 全零文件得到单个共享零块哈希。
- `treeEntryEncodedSize` 与 `json.MarshalV1` 的字节数在两种模式下对全部扫描条目一致。

## 2. 结论摘要

### 2.1 总体判断

本范围内**未发现已确认的 P0**：没有发现未认证的远程接管路径，也没有复现出静默数据丢失。已核查的认证常量时间比较、请求体上限、chunk 路径与范围校验、清单流式编码、锁序、fence 获取与释放顺序、幂等重试等均未发现问题。

主要风险集中在三处：**未提交改动引入的时序与影子树逻辑**（最严重）、**故障条件下的资源保护与恢复路径**、以及**验证能力缺口**（核心承诺缺少真实 SQLite/崩溃注入覆盖）。

### 2.3 最高优先级

1. **F04（P1）**：未提交改动把主节点 `release` 提前到 standby 暂存与激活之前，删除就绪后回滚保护，并使文档、`PRIMARY_OUTAGE_TIMEOUT` 语义与既有 R08 结论失效。
2. **F01（P1）**：restore systemd 单元缺少对 `/run/gitea-replication` 的写权限声明，standby 可能根本无法完成安装（待真实 systemd 验证）。
3. **F05（P2）**：release 之后服务端不再提供 chunk，而新顺序下暂存阶段的按需 chunk 回退发生在 release 之后，一旦触发即 abort 会话。
4. **F17（P2）**：影子树原地复用绕过 `verifyLocal`，全量校验周期承诺的本地重哈希对未变化文件失效。
5. **F18（P2）**：`persistReadyStandbySync` 用未归一化摘要判定交换结果，崩溃恢复路径下影子树基线丢失且旧根残留。

- `validateManifestPathID` 增加 `.stage-current.json` 豁免（`modules/replication/incremental.go:2448`）——这是 shadow 功能的必要修复，改动前 `loadStageBaseManifest` 必然失败并静默禁用该功能。

### 3.2 收益

- 主节点停机窗口从「停止→最终扫描→传输→激活→就绪」缩短为「停止→最终扫描→传输」。
- 影子树原地更新避免每次从活动根重建完整暂存树；无变更时直接短路完成会话。

### 3.3 风险与需要拍板的问题

- **release 语义**（F04/F05）：早释放缩短停机，但文档、超时预算与回滚保护同时失效，且引入 release 后按需取 chunk 必然 404 的确定性失败路径。需要明确选择「恢复就绪后 release」还是「接受在线暂存并同步修改协议、文档与测试」。
- **本地身份信任等级**（F17）：影子树快速路径在 `verifyLocal` 为真时仍只比元数据，需要决定是否接受该信任等级。
- **磁盘预算**（F33/F35）：旧根从「成功后清理」变为「常驻复用」，standby 常驻空间翻倍，容量章节与此矛盾。
- **崩溃恢复路径**（F18）：摘要归一化缺失使影子树复用在最需要的场景失效。
- **测试与文档**（X02、F16、F34）：新增路径零覆盖，README 第 4/5 步、release API 说明、容量章节与成功清理描述都需要同步。

### 4.5 磁盘占用

#### F33 · P2 · 磁盘占用 · 已确认

- 位置：`modules/replication/incremental_client.go:5071`、`modules/replication/install.go:500-503`、`modules/replication/incremental_client.go:4248`、`contrib/replication/README.md:275-278`

#### F34 · P2 · 磁盘占用/可靠性 · 已修复（2026-10-05 第八轮）

### 6.2 磁盘峰值模型

设数据树大小为 D、当前增量块缓存为 C：

| 场景 | 组成 | 峰值（非 reflink） |
| --- | --- | --- |
| 正常运行（未提交改动） | 数据根 D ＋ 常驻影子树（旧根）D ＋ 缓存 C | 约 2D + C（F33） |
| 一次失败激活之后 | 数据根 D ＋ 失败副本 D ＋ 缓存 C | 约 2D + C（F35） |
| 连续失败且保留失败副本期间再次安装 | 数据根 D ＋ 失败副本 D ＋ 待交换暂存 D ＋ 缓存 C | 约 3D + C（F35） |

支持 reflink 的文件系统（btrfs、XFS 等）可共享未变化文件的字节，但目录项与 inode 仍按份数计算；不支持 reflink 时按完整字节计。

## 8. 已核查且未发现问题的点

- **分块算法**：流式读取只使用 128 KiB 池化缓冲，不整文件读入；EOF、文件缩短、无进展、空文件等边界正确；与单缓冲参考实现 10 组输入一致（探针实测）。
- **全零块**：`fullZeroChunkBoundary()` 恒等于 `chunkMaxSize`，满块使用共享零哈希；零块不会被误判为非零。
- **清单编码与上限**：流式分批编码，无整份 `[]byte` 副本；摘要与实际写出在字段集上一致（除 F19 的窄窗口）；`treeEntryEncodedSize` 与真实编码字节一致（探针实测）。
- **摘要与身份校验**：签名比较使用 `hmac.Equal`；身份校验覆盖 Gitea 版本、`APP_WORK_PATH`、实例指纹与通用 token 指纹。
- **清单校验**：块偏移连续无重叠、大小上下界、文件大小等于块和、逻辑大小一致、路径与符号链接目标合法、符号链接链深度受限。
- **路径与打开原语**：`openat2` 的 `RESOLVE_BENEATH|RESOLVE_NO_SYMLINKS` 与逐级 `openat` 回退、`O_NOFOLLOW`、`os.SameFile` 身份复核；原子交换前的同设备、mount ID、无嵌套挂载与无符号链接校验，以及 `RENAME_EXCHANGE` 能力探测。
- **块缓存**：写入前校验 SHA-256，已存在条目先校验再复用，读取时重算并在不匹配时删除；并发写同一哈希用临时文件加 `rename`，结果一致；缓存目录拒绝符号链接并限制权限。
- **持久化原语**：清单写入走临时文件、`fsync`、`rename` 与目录 `fsync`；`current.json` 优先硬链接，失败回退独立写入。
- **控制面认证与请求边界**：Bearer token 常量时间比较，401 不回显 token，token 不进入日志；请求体上限 1 MiB；chunk 哈希与快照 ID 有严格格式校验，无路径注入面。
- **并发与幂等**：锁序统一为 `chunkMu` → `s.mu`，未发现死锁；会话 complete/abort/expire 串行化；preflight/finalize 按 `requestID` 幂等，释放请求对已释放会话返回成功。
- **fence 顺序**：先获取写 fence，再检查 socket 激活，再写 outage 检查点，再停止主节点；错误路径先恢复主节点再释放 fence。
- **只读边界**：中间件按方法拦截，仅放行 GET/HEAD/OPTIONS 与白名单 POST；状态变更 GET 使用黑名单覆盖登录、注册、找回、2FA 与 WebAuthn 等路径；Git 智能 HTTP 与 LFS 只放行下载方向；内部 SSH 白名单与 `routers/private/key.go` 的只读处理闭合；副本模式下不启动 cron，16 处 `queue.Create*` 调用点均包 `GuardPrimaryRecoveryHandler`，认证与懒写路径均有写保护判定。
- **配置校验**：`ENABLED`、`MODE`、`CONTROL_TOKEN` 长度、`SNAPSHOT_DIR` 绝对路径与符号链接、`CONTROL_LISTEN` 仅 loopback、replica 侧 URL 的 HTTPS 与 userinfo 限制、超时为正、服务名固定。
- **部署件**：Polkit 只授予 `git` 对 `gitea.service` 的 start/stop/restart 与固定 switch helper 的 start；Nginx 示例对 `/_replication/` 做来源限制并关闭缓冲。

## 11. 后续重新设计：就地分块补丁安装（2026-10-05）

按用户要求（主要文件系统 ext4、从端不运行 Gitea、不接受每次同步重建暂存树、空间尽量保持 1×、不得延长主节点停机）重新设计了从端安装方式，替代本报告中针对"暂存树 + `RENAME_EXCHANGE`"的一系列结论：

- 从端只在 `APP_WORK_PATH` 维护一棵数据树；更新时按签名清单**就地打补丁**：未变文件零写入，变更文件按 chunk 偏移 `pwrite`，新增文件/符号链接创建，过期条目最后删除，目录元数据与 fsync 最后处理（`modules/replication/apply_inplace.go`）。
- chunk 缓存**边写边释放**：每个 chunk 写完全部清单位置后即从缓存删除；同时预取最多 1 GiB（`deferredChunkCacheLimit`），超出的 chunk 在就地写入时按需取回，因此全新同步与整树全变都不再需要"数据树 + 完整增量缓存"同时存在。测试 `TestInPlaceApplyCreatesTree` 断言应用结束后缓存为空，`TestIncrementalHTTPRoundTripAndSecondDelta` 在缓存上限设为 1 字节时仍完整通过（走延迟按需取数路径）。
- 容量预检改为"尚不存在的条目 + 缺失 chunk 字节"（`inPlaceStageCapacity`），不再按整树复制估算。
- 从端为静态备份节点：不再停/起 `gitea.service`、不再做服务就绪校验；`RestoreLatest` 在服务处于 active 时直接拒绝运行。
- 因此 F01/F02/F11/F13/F16/F34/F37/F39 等针对暂存树、影子树与原子交换的整改/取舍随机制替换而失效；F04（早期 release）与 F27（批量 chunk）结论继续有效。
